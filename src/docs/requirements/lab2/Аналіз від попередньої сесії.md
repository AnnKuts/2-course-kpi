Ключові фрагменти коду
1) Rich-ish доменна модель (інваріант рейтингу + поведінка)
// src/domain/models/Book.ts
set rating(value: number) {
  if (value < 1 || value > 5) throw new DomainError('Рейтинг має бути від 1 до 5');
  this._rating = value;
}
public markAsRead(): void { this.isRead = true; }
2) Фабрика (простi інваріанти)
// src/domain/factories/BookFactory.ts
if (!title.trim()) throw new DomainError('Поле назва книги не може бути порожнім');
if (!author.trim()) throw new DomainError('Поле автор не може бути порожнім');
return new Book(id, title, author, genre, rating, description, isRead);
3) DIP: Application залежить від порту
// src/application/use-cases/BookUseCases.ts
constructor(private readonly bookRepository: IBookRepository) {}
4) Мапер в Infrastructure
// src/infrastructure/mappers/BookMapper.ts
public static toDomain(entity: BookEntity): Book {
  return new Book(entity.id, entity.title, entity.author, entity.genre as Genre, entity.rating, entity.description, entity.isRead);
}
5) Мапінг доменних помилок у HTTP
// src/utils/errorHandler.ts
if (error instanceof NotFoundError) return 404;
if (error instanceof DomainError) return 400;
return 500;
Що варто покращити (щоб “добити” лабу до формальних критеріїв)
- Немає ADR з вибором Anemic vs Rich: не знайшов жодного ADR/docs/adr/*. За фактом у тебе змішано: Book має поведінку (markAsRead) і інваріант рейтингу, але інваріанти title/author живуть у фабриці і легко обходяться мапером/репозиторієм.
- Інваріанти можна обійти через мапер/оновлення:
  - BookMapper.toDomain() створює Book напряму (не через фабрику) → title/author не перевіряються.
  - BookRepository.update() мутує existing.title/author/... без доменної валідації (зараз це частково “прикриває” Zod у контролері, але інваріант має захищати Domain, не Presentation).
- Domain Factory не демонструє “складні інваріанти з БД” через інтерфейс репозиторію (як вимагає PDF). Для книг можна додати, наприклад, перевірку унікальності title+author (або інше правило), передаючи в фабрику порт-репозиторій.
- Зайві/дубльовані помилки: є ще один NotFoundError у src/utils/httpErrors.ts, який конфліктує за назвою з доменним src/domain/errors/NotFoundError.ts (ризик плутанини імпортів).
- “4 окремі пакети/модулі”: у тебе шари є, але також є “поза шарами” src/routes, src/schemas, src/utils, src/middlewares. Формально краще підв’язати їх до Presentation/Infrastructure (наприклад, тримати роутери/DTO/HTTP-мапінг/мідлвари в src/presentation/...), щоб структура максимально відповідала вимозі.

Так — стан Book може стати невалідним, і зараз інкапсуляція/агрегатні правила виконані лише частково.
- Чи може стан Book стати невалідним при прямій зміні полів
  - Так. У src/domain/models/Book.ts поля title, author, genre, description, isRead — публічні й мутабельні. Їх можна змінити напряму без жодних перевірок. Інваріант захищено лише для rating через setter.
- Чи всі поля інкапсульовані та недоступні напряму
  - Ні. Інкапсульовано тільки _rating (private) + доступ через getter/setter. Решта — відкриті.
- Чи зміна стану відбувається виключно через методи агрегата, а не в репозиторії
  - Ні. Репозиторій напряму мутує поля доменного об’єкта:
    - src/infrastructure/repositories/book.repository.ts: в update() робиться existing.title = ..., existing.author = ..., existing.genre = ..., existing.description = ..., existing.isRead = ... (це обходить будь-які доменні правила, крім rating).
  - Use case теж змінює стан напряму:
    - src/application/use-cases/BookUseCases.ts: RateBookUseCase робить book.rating = rating (це ок, бо setter валідить), але потім передає в repo update(id, book) — що типово не DDD-стиль (repo має працювати з агрегатом як цілим, або use case викликає доменні методи і зберігає агрегат).
- Чи є Book єдиною точкою доступу до поведінки (Aggregate Root)
  - Частково. Вся поведінка дійсно “всередині” Book (markAsRead, валідація рейтингу), і репозиторій працює з Book як з єдиною сутністю.
  - Але межа агрегата розмита, бо зовнішній код (repo/use case/controller) може напряму міняти стан (title/author/...), тобто Book не є “єдиною точкою” керування своїми правилами.
- Rich Model чи просто структура даних
  - “Напів-rich”:
    - Rich: markAsRead() і інваріант rating в src/domain/models/Book.ts.
    - Anemic: більшість полів — просто дані без поведінки/валідації; основна валідація зараз у Zod (src/schemas/book.schema.ts) та у фабриці (src/domain/factories/BookFactory.ts), але це легко обходиться мапером/репозиторієм.
- Чи репозиторій порушує інваріанти, змінюючи поля напряму
  - Потенційно так:
    - Може встановити title = '' або author = '' (бо BookFactory це перевіряє, але update() в repo — ні).
    - Може виставити genre будь-яким рядком через мапер (entity.genre as Genre у src/infrastructure/mappers/BookMapper.ts — це unsafe cast; якщо в БД “сміття”, домен це проковтне).
    - rating репозиторій змінює через existing.rating = ..., і це якраз захищено setter’ом (тобто тут інваріант не зламаєш, якщо зміна йде через setter).
- Які інваріанти реально гарантує агрегат зараз і як захищаються
  - Гарантує:
    - 1 <= rating <= 5 — захищено в src/domain/models/Book.ts setter’ом.
  - Частково/не гарантовано доменом:
    - title не порожній — перевіряється лише у src/domain/factories/BookFactory.ts, але може бути обійдено через BookMapper.toDomain() і BookRepository.update().
    - author не порожній — те саме.
    - genre валідний — строго не гарантується, бо BookMapper робить каст, а не перевірку.
- Чи створення Book гарантує валідний стан
  - Лише якщо створювати через BookFactory.create() (src/domain/factories/BookFactory.ts).
  - Але валідність не гарантована глобально, бо:
    - Book можна створити напряму через new Book(...) (і так робить BookMapper.toDomain() у src/infrastructure/mappers/BookMapper.ts та BookRepository.create() повертає new Book(...) у src/infrastructure/repositories/book.repository.ts).
    - Конструктор Book не перевіряє title/author/genre/description/isRead, тільки примусово проганяє rating через setter.
- Які поля варто винести у Value Objects і чому
  - Title — щоб заборонити порожні/“пробільні” значення і мати єдине місце нормалізації (trim, max length).
  - AuthorName — те саме.
  - Rating — щоб інваріант “1..5” був типом, і його не можна було обійти (зараз це вже майже так, але VO прибере “голе число” з API домена).
  - (Опційно) BookId — щоб не тягати number і випадково не змішувати з іншими id.
  - Genre у тебе вже є enum (src/domain/models/Genre.ts) — це ок як VO-подібна концепція, але мапер має робити строгий parse/guard, а не as Genre.
- Чи відповідає реалізація принципам DDD Aggregate Root і де порушення (точки)
  - Порушення інкапсуляції/керування інваріантами:
    - Публічні поля в src/domain/models/Book.ts дозволяють обхід правил (агрегат не контролює власний стан).
  - Порушення “зміни через методи агрегата”:
    - src/infrastructure/repositories/book.repository.ts update() мутує агрегат напряму.
  - Порушення “anti-corruption/validation при мапінгу”:
    - src/infrastructure/mappers/BookMapper.ts робить небезпечний каст entity.genre as Genre, що може занести невалідний стан у домен.
  - Порушення “створення агрегата гарантує валідність”:
    - new Book(...) використовується поза фабрикою (мапер, репо), а конструктор не гарантує всі інваріанти.

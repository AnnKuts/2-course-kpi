# Лабораторна робота 5: Аналіз модульного моноліту

## Аналіз лабораторної 5

### Як визначені межі контекстів?

Система була поділена на два обмежені контексти:

**Core** — основний контекст, що містить всю бізнес-логіку управління бібліотекою:
доменну модель `Book` з інваріантами (рейтинг 1–5, унікальність за назвою та автором),
фабрику, репозиторії та всі command/query хендлери.

**Analytics** — аналітичний контекст з власною моделлю `BookMetric`. Це read-only
споживач: він не змінює жодних даних у Core, лише підписується на події та будує власні
проєкції у таблиці `analytics_metrics`.

**Альтернативи, які розглядалися:**
- `Catalog + Management` — поділ за read/write операціями. Відхилено, бо CQS вже
  реалізовано на рівні application layer; поділ на два модулі не дав би нового
  архітектурного ефекту.
- `Books + Users + Analytics` — введення контексту `Users`. Відхилено, бо в системі
  немає поняття користувача — виділення потребувало б суттєвих змін у домені.

Обрано `Core + Analytics` як найбільш природний поділ: одна відповідальність —
управляти книгами, інша — збирати метрики.

### Як ACL захищає модулі від змін?

ACL реалізовано в `src/analytics/acl/BookEventTranslator.ts`. Він перехоплює
`BookCreatedEvent` (зовнішній контракт Core) та перекладає його у `BookMetric`
(внутрішня модель Analytics):

```
BookCreatedEvent (Core contract)
        ↓
BookEventTranslator (ACL — belongs to Analytics)
        ↓
BookMetric (Analytics internal model)
```

Завдяки цьому: якщо Core додасть нові поля до події або перейменує існуючі,
Analytics треба оновити лише один клас — `BookEventTranslator`. Весь інший код
Analytics (хендлер, репозиторій, доменна модель) залишається незмінним.

Зовнішня модель не проникає далі ACL: `OnBookCreatedHandler` отримує вже
перекладений `BookMetric`, а не `BookCreatedEvent`.

### Де strong consistency, а де eventual consistency?

**Strong consistency — в межах Core:**
Операція `CreateBook` є атомарною всередині одного модуля:
1. Фабрика валідує дані та перевіряє дублікати (один SQL-запит).
2. Репозиторій зберігає книгу (другий SQL-запит).
3. Синхронний аудит (`ConsoleAuditService.logBookCreated`) — завершується до відповіді.
4. HTTP-відповідь `201 Created` повертається.

Якщо будь-який крок 1–3 кидає виняток — книга не зберігається. Це передбачуваний,
послідовний потік без будь-якої затримки між операціями.

**Eventual consistency — між Core та Analytics:**
Після кроку 4 EventBus публікує `BookCreatedEvent` через `setTimeout(0)`, тобто
вже після того, як HTTP-відповідь надіслана клієнту. `OnBookCreatedHandler` обробляє
подію асинхронно і записує `BookMetric` в `analytics_metrics`.

Це означає: одразу після `POST /books` запит `GET /analytics` може ще не відображати
нову книгу. Це прийнятно для бізнесу — метрики є аналітичним інструментом, незначна
затримка (мілісекунди в поточній реалізації, секунди/хвилини в production з реальним
брокером) не впливає на коректність основного сценарію.

### Що зміниться при виділенні аналітики в окремий сервіс?

**Не зміниться:**
- Внутрішня архітектура `Analytics` модуля — вся логіка залишається.
- `BookEventTranslator` — ACL вже ізолює від змін у Core.
- Доменна модель `BookMetric` та `AnalyticsRepository`.

**Зміниться:**
- `InMemoryEventBus` треба замінити на реальний брокер (RabbitMQ, Kafka, Redis Pub/Sub).
- `AnalyticsModule` більше не отримує той самий `eventBus` instance — замість цього
  підписується на топік/чергу брокера.
- Зберігання: окрема БД замість спільного SQLite-файлу.
- Деплоймент: окремий процес/контейнер.

Все це — зміни в `server.ts` (Composition Root) та infrastructure шарі. Доменна логіка
та ACL залишаються незмінними — саме це і є головна перевага модульного моноліту.

## Ретроспектива курсу: від лабораторної 1 до 5

### Як змінювалася архітектура

**Лабораторна 1 — "Сирий" моноліт:**
Уся логіка — контролер, SQL-запити, бізнес-правила — в одному місці. Немає шарів,
немає абстракцій. Будь-яка зміна ламала непов'язані частини.

```
HTTP → Controller → [SQL + logic mixed together] → Response
```

**Лабораторна 2 — Доменна модель та шарова архітектура:**
Введено `Book` як rich domain model з інваріантами (рейтинг, isRead). З'явився
`BookFactory` для безпечного створення, `BookMapper` для перетворення між шарами.
Логіка перемістилася в домен, контролер став "тонким".

```
HTTP → Controller → Service → Domain → Repository → DB
```

**Лабораторна 3 — CQS та репозиторії:**
Розділено читання та запис: `IBookReadRepository` і `IBookWriteRepository`. Замість
одного сервісу — окремі `CommandHandler` та `QueryHandler` для кожної операції.
Це зробило код значно легшим для тестування (кожен хендлер — незалежна одиниця).

```
HTTP → Controller → CommandHandler → WriteRepository → DB
                  → QueryHandler  → ReadRepository  → DB
```

**Лабораторна 4 — Синхронна та асинхронна комунікація:**
Введено `InMemoryEventBus` та `BookCreatedEvent`. Після збереження книги система
публікує подію — підписники (`ConsoleAuditService`) обробляють її незалежно від
основного потоку. Додано синхронний варіант через `IAuditService` з try/catch для
порівняння обох підходів.

```
HTTP → Handler → [save] → [sync audit] → [publish event] → Response
                                                  ↓ (async)
                                        ConsoleAuditService.handle()
```

**Лабораторна 5 — Модульний моноліт:**
Вся система поділена на ізольовані bounded contexts. Кожен модуль — окрема папка з
повною внутрішньою архітектурою та явним публічним контрактом. Міжмодульна комунікація
виключно через події. ACL захищає внутрішні моделі від зовнішніх змін.

```
[Core Module]          [Analytics Module]
  CoreModule ────────────────────────────────
  BookFactory            OnBookCreatedHandler
  CreateBookHandler  ←event─  BookEventTranslator (ACL)
  EventBus.publish() ────→    BookMetric
                              AnalyticsRepository
```

### Які архітектурні рішення виявилися найціннішими?

**1. Instance-based BookFactory з async перевіркою дублікатів.**
Перетворення фабрики з static-класу на instance з ін'єкцією `IBookReadRepository`
дозволило перевіряти унікальність прямо при створенні — на рівні домену, а не
в контролері або сервісі. Це єдине місце, де правило "не можна мати дві однакові
книги" зафіксоване і завжди виконується.

**2. Розділення `IBookReadRepository` та `IBookWriteRepository`.**
CQS на рівні репозиторіїв — дозволяє незалежно масштабувати читання і запис,
мокати лише потрібний бік у тестах, і в майбутньому замінити read-side на
денормалізоване сховище без зміни write-side.

**3. InMemoryEventBus з `setTimeout(0)`.**
Простий, але ефективний механізм асинхронної доставки. Дозволив продемонструвати
eventual consistency без зовнішніх залежностей, повністю тестабельний з `:memory:` SQLite.

**4. `initDb(filename?)` — підтримка in-memory SQLite.**
Один параметр зробив інтеграційні тести повністю ізольованими, швидкими
(немає файлового I/O) і незалежними від стану між запусками.

### Що було б зроблено інакше?

**Ввести `BookReadModel` з самого початку.**
У лабораторній 2–3 `IBookReadRepository.findById` повертав `Book` (domain entity).
Це порушує CQRS — read-side не повинен повертати mutable domain objects. Перехід
на `BookReadModel` (plain DTO) правильний, але потребував рефакторингу репозиторіїв,
хендлерів та тестів.

**Додати `parseGenre()` одразу в `BookMapper`.**
`entity.genre as Genre` — небезпечний cast, який ховає потенційну помилку БД.
Захисна валідація з `DomainError` мала бути частиною маппера з лабораторної 2.

**Спланувати публічні контракти раніше.**
Рефакторинг для lab5 міг би бути набагато простішим, якби з lab3 кожен модуль
мав explicit `index.ts` — єдину точку входу. Тоді перехід до модульного моноліту
вимагав лише формалізації вже існуючих меж.

### Trade-offs між простотою та гнібкістю

| Рішення | Простота | Гнучкість | Обраний компроміс |
|---------|----------|-----------|-------------------|
| Static vs Instance Factory | Static простіший | Instance — ін'єктабельний, тестабельний | Instance (важливіше тестування) |
| InMemory vs Real EventBus | InMemory — без залежностей | Real bus — масштабується | InMemory (легко замінити через IEventBus) |
| Sync vs Async audit | Sync — простіший потік | Async — не блокує відповідь | Обидва (навчальна мета: порівняти) |
| Strong vs Eventual consistency | Strong — простіше розуміти | Eventual — масштабується | Strong всередині модуля, Eventual між модулями |
| Modular monolith vs Microservices | Моноліт — один деплоймент | Мікросервіси — незалежний масштаб | Модульний моноліт (готовий до виділення) |

# ADR-001: Поділ системи на bounded contexts

## Статус

Прийнято

## Контекст

Після чотирьох лабораторних система має повний набір доменних правил, CQS-архітектуру та
асинхронну комунікацію через EventBus. Вся логіка живе в одному просторі — усі сутності,
репозиторії та хендлери мають доступ одне до одного без явних меж.

Завдання лабораторної 5 — перетворити систему на модульний моноліт: виділити bounded
contexts з явними публічними контрактами та заборонити пряму міжмодульну залежність.

## Розглянуті варіанти

### Варіант A: Core + Analytics (обраний)
Основний контекст обробляє всю бізнес-логіку (CRUD книг, валідація, доменні правила).
Analytics — ізольований read-only модуль, що збирає метрики через події.

### Варіант B: Catalog + Management
Поділ за операціями: `Catalog` (перегляд, пошук) і `Management` (створення, редагування,
видалення). Більш природний поділ за read/write, але в системі вже є CQS на рівні
application layer — додатковий поділ на модулі не дав би нової архітектурної цінності.

### Варіант C: Books + Users + Analytics
Введення модуля `Users` (хто додав книгу, хто читав). Поточна система не має поняття
користувача — виділення цього контексту потребувало б значних змін у доменній моделі.

## Рішення

Обрано **Варіант A: Core + Analytics**.

**Core module** (`src/core/`):
- Містить всю існуючу бізнес-логіку: доменну модель `Book`, фабрику, репозиторії,
  командні та запитові хендлери, контролер.
- Публікує `BookCreatedEvent` після кожного успішного створення книги.
- Публічний контракт: `CoreModule` (клас з `router`) у `src/core/api.ts`.

**Analytics module** (`src/analytics/`):
- Власна доменна модель: `BookMetric` — агрегат, що представляє факт додавання книги
  з точки зору аналітики (не повторює структуру `Book`).
- Підписується на `BookCreatedEvent` через EventBus.
- ACL (`BookEventTranslator`) перекладає зовнішню подію у внутрішню модель.
- Зберігає метрики у власній таблиці `analytics_metrics`.
- Публічний контракт: `AnalyticsModule` у `src/analytics/api.ts`.

## Обґрунтування

1. **Природна відповідальність:** Core — управляє книгами. Analytics — відповідає за
   збір та зберігання метрик. Ці відповідальності не перетинаються.
2. **Read-only споживач:** Analytics нічого не змінює в Core — лише читає події.
   Це унеможливлює зворотній зв'язок і циклічні залежності.
3. **Демонстрація eventual consistency:** Core завершує операцію одразу, Analytics
   обробляє подію асинхронно — це чіткий і зрозумілий приклад eventual consistency.
4. **ACL як захист:** якщо структура `BookCreatedEvent` у Core зміниться, Analytics
   треба оновити лише `BookEventTranslator`, а не всі внутрішні компоненти.

## Наслідки

**Позитивні:**
- Модулі не мають прямих залежностей на внутрішні класи один одного.
- Додавання нового підписника (наприклад, `Notifications`) не вимагає змін у Core.
- При виділенні Analytics в окремий мікросервіс зміниться лише транспорт (InMemoryEventBus
  → Kafka/RabbitMQ), але не логіка модуля.

**Негативні:**
- Дані в Analytics завжди трохи відстають від Core (eventual consistency).
- `BookCreatedEvent` є спільним контрактом — його зміна вимагає оновлення обох модулів.

# ADR 001: Вибір підходу до доменної моделі

**Дата**: 2026-05-03  
**Статус**: Прийнято

## Контекст

Лабораторна робота 2 вимагає явно обрати підхід до доменної моделі: **Anemic** або **Rich Domain Model** — і зафіксувати рішення з обґрунтуванням.

Проєкт: система управління бібліотекою книг (CRUD + рейтинг + статус прочитано).

## Рішення

Обрано **Anemic Domain Model**.

## Обґрунтування

### Чому Anemic підходить для цього проєкту

1. **Простий домен**: система має лише одну сутність (`Book`) і мінімальний набір бізнес-правил:
   - рейтинг від 1 до 5
   - назва і автор не можуть бути порожніми
   - книга з такою самою назвою та автором не може бути додана двічі
   - позначення книги як прочитаної

2. **Відсутність складних переходів стану**: `Book` не має складного lifecycle (порівняно, наприклад, з `Booking`, який проходить `created → confirmed → cancelled`). Стан `isRead` — простий boolean-перехід.

3. **Немає ризику дублювання логіки**: оскільки сутність одна і use case'ів небагато, правила не ризикують розпорошитися між кількома сервісами.

4. **KISS**: Rich Model виправдана, коли є складна бізнес-логіка, яку потрібно захистити і яка ризикує дублюватися. Для поточного домену це overengineering.

### Що реалізовано у моделі

`Book.ts` містить:
- `private _rating` з getter/setter — **мінімальна інкапсуляція** одного інваріанту (rating 1–5), що є захистом від невалідного стану навіть в Anemic-підході
- `markAsRead()` — зручний метод, що змінює `isRead = true`
- Решта полів (`title`, `author`, `genre`, `description`) — публічні

Ці два елементи не роблять модель "Rich" — вони є прагматичним доповненням, яке прийнятне в Anemic-підході.

### Відповідальність за інваріанти

| Інваріант | Де захищено |
|-----------|-------------|
| `rating` від 1 до 5 | `Book` setter + `BookFactory.create()` |
| `title`, `author` не порожні | `BookFactory.create()` |
| Унікальність `title + author` | `BookFactory.create()` через `IBookRepository` |
| Формат вхідних даних (HTTP) | Zod-схема у `src/schemas/book.schema.ts` |

### Альтернатива, що не була обрана

**Rich Domain Model** — додала б приватні поля для `title`, `author` і методи `updateTitle()`, `updateAuthor()` з перевірками. Це збільшило б обсяг коду без реальної вигоди для домену такого масштабу. Якщо домен зросте (наприклад, з'явиться логіка позик, резервування, повернень) — перехід до Rich буде виправданим.

## Наслідки

- Validation логіка при створенні сконцентрована в `BookFactory`
- При оновленні — validation у Application Layer (`UpdateBookUseCase`)
- Доменна модель залишається простою і легкою для тестування

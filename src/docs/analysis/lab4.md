# Лабораторна робота 4: Аналіз синхронної та асинхронної комунікації

## Що змінилося порівняно з лабораторною 3?

У лабораторній 3 була впроваджена архітектура CQS: усі операції запису виконуються
через Command Handlers, читання — через Query Handlers. Комунікація була строго лінійною:

```
HTTP → Controller → CommandHandler → Repository → DB
```

Лабораторна 4 розширює цей потік **комунікацією побічних ефектів**. Після створення
книги система має також зафіксувати операцію в журналі аудиту. Реалізовано та порівняно
два підходи:

```
HTTP → Controller → CreateBookCommandHandler
                         ├── BookFactory.create()     (доменна валідація)
                         ├── WriteRepository.create() (збереження)
                         ├── auditService.logBookCreated(event)  ← СИНХРОННИЙ виклик
                         └── eventBus.publish(event)             ← АСИНХРОННА публікація
                                   └── [мікротаск] ConsoleAuditService.handle()
```

## Виділений побічний компонент та обґрунтування вибору

**Компонент:** `ConsoleAuditService` — журнал аудиту, що фіксує кожне створення книги.

**Чому аудит?**
- Природній побічний ефект: основна бізнес-задача — створення книги, логування є вторинним.
- Збій аудиту не повинен скасовувати збереження книги.
- Чітко демонструє обидва патерни комунікації без надмірної складності.

**Розміщення:** `src/audit/` — окремий пакет із власними контрактами:
- `IAuditService` — інтерфейс для синхронного виклику
- `IEventHandler<BookCreatedEvent>` (з `application/events/`) — для асинхронної підписки

## Синхронна комунікація

**Реалізація:** `CreateBookCommandHandler` отримує `IAuditService` через ін'єкцію
в конструктор і викликає `auditService.logBookCreated(event)` напряму після збереження книги.

```typescript
// CreateBookCommand.ts — синхронний виклик
try {
  this.auditService.logBookCreated(event); // той самий потік, блокує до завершення
} catch (auditError) {
  console.error('[CreateBookHandler] Sync audit failed (ignored):', auditError);
}
```

**Рішення щодо обробки помилок:** `log and ignore` — помилка аудиту перехоплюється
і логується. Книга зберігається, HTTP-відповідь повертається. Аудит — некритичний
побічний ефект.

### Спостереження

| Параметр | Значення |
|----------|----------|
| Час відповіді API | Включає час виконання аудиту. `logBookCreated` є синхронним і швидким (console.log ~0мс), але повільний аудит (запис у файл, звернення до БД) безпосередньо збільшив би час HTTP-відповіді. |
| Поведінка при збої | Помилка перехоплюється і логується. Основна операція успішна, HTTP-відповідь — `201 Created`. |
| Чи знає Handler про реалізацію? | **Ні.** Залежність лише від інтерфейсу `IAuditService`. Конкретний `ConsoleAuditService` підключається в `server.ts` (Composition Root). |
| Зв'язаність між компонентами | Вища: Handler має залежність на `IAuditService` на рівні компіляції. |

## Асинхронна комунікація

**Реалізація:** Після збереження книги Handler публікує `BookCreatedEvent` в `InMemoryEventBus`.
Шина доставляє подію через `setTimeout(0)`, тому підписники виконуються вже після завершення
поточного стека викликів.

```typescript
// InMemoryEventBus.ts — асинхронна доставка
eventHandlers.forEach(handler => {
  setTimeout(() => {
    handler.handle(event).catch(error => {
      console.error(`[EventBus] Помилка обробки ${event.eventName}:`, error);
    });
  }, 0);
});
```

`ConsoleAuditService.handle()` підписаний і симулює затримку 500мс.

### Спостереження

| Параметр | Значення |
|----------|----------|
| Час відповіді API | **Не** включає час виконання підписників. HTTP `201` повертається одразу, а `ConsoleAuditService.handle()` виконується через ~500мс після відповіді. |
| Поведінка при збої | Помилка перехоплюється в середині EventBus і логується. Основна операція та HTTP-відповідь не зачіпаються. |
| Чи знає Handler про реалізацію? | **Ні.** Залежність лише від `IEventBus`. Підписники реєструються в `server.ts`. |
| Зв'язаність між компонентами | Нижча: Handler знає лише тип події, а не хто її обробляє. Нових підписників можна додавати без зміни Handler. |

## Порівняльна таблиця

| Критерій | Синхронна | Асинхронна |
|----------|-----------|------------|
| Час відповіді API | Довший: включає виклик аудиту | Короткий: Handler повертається одразу |
| Поведінка при збої | Налаштовується (викинути або проковтнути) | Завжди ізольована (помилки логуються шиною) |
| Зв'язаність між компонентами | Середня (залежність від інтерфейсу) | Низька (лише контракт події) |
| Гарантія порядку виконання | Так — аудит до відповіді | Ні — підписник виконується після відповіді |
| Простота тестування | Проста: мок `IAuditService`, перевірка виклику | Потребує врахування відкладеного виконання |
| Складність реалізації | Низька | Середня (потрібна інфраструктура Event Bus) |
| Спостережуваність | Легко — той самий стек трасування | Складніше — помилки в окремому асинхронному контексті |

## Який підхід обрати для production?

**Асинхронний (Event Bus) для побічних ефектів: аудит, сповіщення, аналітика.**

Причини:
1. **Час відповіді:** HTTP-відповідь не повинна залежати від систем логування чи сповіщень. Повільне сховище аудиту (наприклад, запис у зовнішній сервіс) деградувало б API у синхронному варіанті.
2. **Стійкість:** Якщо сервіс аудиту недоступний — книги все одно мають створюватися. Асинхронне розв'язання забезпечує це без try/catch у кожному Handler.
3. **Розширюваність:** Додавання нового підписника (аналітика, email-сповіщення) не вимагає жодних змін у Command Handler.

**Синхронна комунікація — для критичних перевірок**, які ОБОВ'ЯЗКОВО мають завершитися
до виконання основної операції: перевірка шахрайства, перевірка квоти, авторизація другого
фактору. Це не побічні ефекти, а передумови — вони мають кидати помилку, а не ігноруватися.

## Ідемпотентність обробників

**`ConsoleAuditService.handle()` є ідемпотентним у тому сенсі, що дворазовий виклик
не пошкоджує стан** — просто логується двічі. Для `console.log`-аудиту дублікати
нешкідливі (лише зайвий рядок у логах).

У production-системі (наприклад, запис аудиту в базу даних) обробник **за замовчуванням**
не є ідемпотентним. Щоб зробити його ідемпотентним:
- Зберігати `event.occurredAt` + `event.eventName` + `event.bookId` як складений унікальний ключ.
- Перед вставкою перевіряти, чи вже існує такий запис.
- Якщо так — пропускати вставку без помилки.

Цей патерн називається **Exactly-Once Processing** і є стандартним підходом для систем
з гарантією доставки «щонайменше один раз» (RabbitMQ, Kafka).

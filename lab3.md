# Аналіз впровадження CQS (Лабораторна робота 3)

## Що змінилося в структурі проєкту порівняно з лабораторною 2?

У лабораторній роботі 2 ми використовували монолітні `BookUseCases`, де всі операції (і читання, і запис) були згруповані разом. Архітектура спиралася на єдиний `BookRepository`, який обробляв усі взаємодії з базою даних і повертав повноцінні доменні моделі (`Book`).

У поточній реалізації (lab 3) ми впровадили патерн CQS (Command-Query Separation):
1. **Розділення Application Layer**: Замість єдиного файлу з Use Cases, ми створили папки `commands` та `queries`. Кожна операція тепер є окремим класом (наприклад, `CreateBookCommandHandler`, `GetAllBooksQueryHandler`).
2. **Розділення репозиторіїв**: Замість одного `BookRepository` з'явилися `IBookWriteRepository` (тільки для мутацій) та `IBookReadRepository` (тільки для вибірки даних).
3. **DTO замість доменних моделей при читанні**: Запити тепер повертають `BookReadModel` (DTO), а не доменну сутність `Book`. Команди ж навпаки приймають прості DTO (`Command`) і не повертають сутності (максимум — `id` створеного запису).
4. **Тонкі контролери**: `BookController` більше не містить ніякої бізнес-логіки. Його єдина задача — перетворити HTTP-запит у відповідний Command/Query DTO і передати його в Handler.

## Переваги CQS: чим допомогло розділення?

1. **Чітка відповідальність (SRP)**: Кожен Handler робить тільки одну річ. Це робить код більш передбачуваним і легким для розуміння.
2. **Спрощення тестування**: Unit-тести для команд стали набагато простішими. Нам не потрібно мокати складні запити з БД — достатньо перевірити, чи правильно відпрацював домен і чи викликався метод `save`/`update` репозиторію.
3. **Оптимізація читання**: Оскільки Query повертає `ReadModel` (DTO), ми можемо оптимізувати SQL-запити. Нам більше не потрібно "підіймати" важку доменну модель, валідувати її інваріанти просто для того, щоб віддати JSON на клієнт.

## Недоліки CQS: що ускладнилося?

1. **Більше коду (Boilerplate)**: Замість одного класу UseCase і одного репозиторію ми тепер маємо десятки невеликих файлів (окремий файл для кожної команди/запиту, два репозиторії).
2. **Складність навігації**: Розробнику, який вперше бачить проєкт, може бути складніше знайти, де саме виконується та чи інша логіка, оскільки вона "розкидана" по багатьох дрібних файлах.

## Чим підхід з Command / Query Handler відрізняється від Service, який робить все сам?

Традиційний Application Service зазвичай стає "God Object" (Божественним об'єктом), який містить десятки методів, інжектить у себе безліч репозиторіїв та залежностей. Це призводить до розростання конструктора і складності мокування в тестах.

Підхід з Handlers ізолює кожну операцію. `CreateBookCommandHandler` має лише ті залежності, які йому потрібні для створення (наприклад, `IBookWriteRepository` і `BookFactory`). Він не знає про логіку видалення чи пошуку, що робить його максимально сфокусованим.

## Як CQS впливає на розширюваність?

CQS робить розширюваність (Extensibility) системи набагато безпечнішою:
- **Щоб додати нову фічу (наприклад, команду архівування книги)**: ми просто створюємо новий файл `ArchiveBookCommand.ts` зі своїм Handler. Ми **не змінюємо** існуючий код (дотримання Open/Closed Principle). У підході з Service нам довелося б лізти в гігантський файл і додавати новий метод, ризикуючи зламати щось інше.
- **Щоб оптимізувати існуючий запит**: ми просто змінюємо один `QueryHandler` та SQL-запит в `ReadRepository`, не зачіпаючи логіку запису або доменну модель.

## Чи відрізняється структура даних, яку повертає Query, від доменної моделі? Чому це важливо?

Так, дуже суттєво відрізняється.
У лабораторній роботі 2 кожен запит діставав з БД дані, пропускав їх через `BookMapper` для створення доменного об'єкта `Book` (з методами, приватними полями, валідацією), а потім контролер перетворював це назад у JSON. Це зайве навантаження на процесор і пам'ять.

У поточній реалізації Query повертає `BookReadModel` — звичайний об'єкт (DTO), який точно відповідає тому, що очікує клієнт.
Це важливо, оскільки:
1. **Продуктивність**: Ми уникаємо інстанціювання складних доменних моделей.
2. **Гнучкість**: Якщо для екрану зі списком книг нам потрібно повернути об'єднані дані з кількох таблиць (наприклад, разом з іменем автора з іншої таблиці), `ReadModel` дозволяє легко це зробити за допомогою SQL `JOIN`, не порушуючи "чистоту" доменної моделі. Доменна модель використовується виключно для мутацій та захисту бізнес-правил.
